# vless-tunnel-openwrt — вводная для агента

Документ для передачи задачи: что решено, почему, и что делать дальше.
Не спецификация «на будущее» — это текущее состояние проекта на момент передачи.

## Задача

Минимальный клиент выборочной маршрутизации для OpenWrt: нужные ресурсы в
туннель VLESS, всё остальное напрямую. Порт идеи с десктопного проекта
`github.com/RamDll/vless-tunnel` (Ubuntu, TPROXY + Xray, ~2600 строк bash).
Целевой объём здесь — 600–800 строк.

## Железо и система

| | |
|---|---|
| Роутер | Cudy WR3000S v1 |
| SoC | MediaTek MT7981 (filogic), 2×Cortex-A53 |
| Архитектура | aarch64 (`aarch64_cortex-a53`) |
| RAM | 234 МБ + 116 МБ swap |
| Флеш | 94 МБ overlay, свободно ~92 МБ после удаления podkop |
| Прошивка | OpenWrt 25.12.5, ядро 6.12.94 |
| Пакетный менеджер | apk (opkg больше нет) |

## Ключевое ограничение: ядро только Xray

Сервер использует **XHTTP + VLESS Encryption (mlkem768x25519plus)**.
Апстримный sing-box не умеет ни того, ни другого — XHTTP это транспорт Xray,
а поле `encryption` теряется при любой конвертации в sing-box JSON, после чего
сервер не принимает соединение. Симптом: ссылка импортируется без ошибок,
SOCKS CONNECT проходит, HTTP-байт нет.

Практическая проверка владельцем: из всего испробованного заработал только
форк podkop с расширенным sing-box. Отсюда решение — Xray-core, и отсюда же
смысл писать своё вместо использования готового комбайна.

**Не предлагать sing-box, mihomo, clash как «более удобную» замену.**
Это не вопрос удобства, это вопрос поддержки протокола.

Проверено на реальном железе: `apk add xray-core` ставит `26.3.27`, команда
`xray vlessenc` подтверждает поддержку VLESS Encryption — скачивать релиз
с GitHub не нужно, версия из apk-фида подходит.

## Архитектурные решения

**Решение «туннель или напрямую» принимает Xray через sniffing, а не
nftables по DNS-наблюдению.** Это ревизия исходного плана (см. «Эволюция
архитектуры» ниже, почему) — сделано осознанно, с конкретной причиной, не
случайный дрейф. Остальные решения ниже не пересматривались.

TPROXY в nftables перехватывает **весь** TCP/UDP-трафик LAN-клиентов (кроме
приватных сетей и ручного bypass-списка). Внутри Xray — два outbound'а,
`proxy` (VLESS) и `direct` (freedom), и `routing.rules`, которые матчат по
домену (из `domains`, вставлен как `domain:...` inline-список, без
geosite.dat) или по IP (из `subnets`). Домен для матчинга Xray берёт не из
DNS-ответа, а через **sniffing** прямо из TLS SNI / HTTP Host / QUIC
заголовка самого соединения (`sniffing.routeOnly: true` — домен участвует
только в выборе outbound'а, реальное соединение и для proxy, и для direct
идёт на исходный IP, увиденный TPROXY, без своего DNS-резолва внутри Xray).

Следствия:
- **Устойчиво к DNS-over-HTTPS/DoT на клиенте.** Не зависит от того, дошёл
  ли DNS-запрос клиента до роутера — решение принимается по содержимому
  самого соединения. Живьём проверено: клиент, резолвящий на прямую
  внешний DNS (в обход роутера), всё равно корректно тоннелируется по
  домену — см. «Проверено на реальном железе» ниже.
- **dnsmasq не нужен вовсе** (ни `dnsmasq-full`, ни `confdir`, ни
  `nftset=`) — вся эта прослойка и связанный с ней класс багов исчезли
  вместе с архитектурой, которая в них нуждалась.
- **geo-файлы всё ещё не ставятся** — используется свой `domains`-список
  (уже существовал, теперь просто вставляется в `routing.rules` напрямую),
  а не geosite.dat/geoip.dat.
- **Обратная сторона**: через Xray (userspace) теперь проходит весь
  TCP/UDP-трафик LAN, а не только явно нужный — то, что решится идти
  `direct`, тоже сначала пройдёт TPROXY→Xray→freedom-outbound, а не
  прямую пересылку ядра с hardware-offload. Раньше через userspace шло
  только туннелируемое; offload сохранялся для всего остального. Осознанно
  принятая цена устойчивости к DoH — см. «Эволюция архитектуры».
- **Не работает для не-TLS/HTTP/QUIC протоколов** — если сниффинг не может
  извлечь домен (например, Telegram MTProto — не TLS), решение падает в
  default-правило `direct`, даже если сам домен есть в `domains`. Митигация
  — добавить известные IP-диапазоны такого сервиса в `subnets` (матчинг по
  IP не зависит от протокола/sniffing). См. открытые вопросы.

Остальные решения (не пересматривались):

1. **Перехватывается только транзитный трафик клиентов LAN.** Роутер сам
   ходит напрямую. Следствие: TPROXY в `prerouting` работает штатно, петля
   невозможна, не нужны ни `local default dev lo` для output, ни исключение
   Xray по uid, ни `--exclude-user` из десктопной версии. Плюс невозможно
   отрезать себе SSH.

2. **Правила живут в `/etc/nftables.d/`, внутри `table inet fw4`.** fw4
   инклюдит их сам при `fw4 reload`, рестарте сети, поднятии WAN.
   Watchdog-таймер из десктопной версии здесь не нужен вообще.

3. **ucode вместо python3.** Разбор `vless://` и генерация `config.json` —
   на ucode, он уже есть на любом OpenWrt с fw4 и умеет JSON нативно.
   Python ради парсинга URI на роутер не тащим (десятки МБ).

4. **Распространение — установочный скрипт, не `.apk`.** В 25.12 запрещена
   установка неподписанных пакетов; свой `.apk` означал бы либо просить
   пользователя добавить ключ в `/etc/apk/keys`, либо приучать к
   `--allow-untrusted`. Скрипт качает всё в `/tmp`, проверяет sha256 и
   только потом трогает систему. `.apk` — возможный второй шаг, когда
   устаканится.

5. **IPv6 обрабатывается симметрично IPv4.** Раньше на старте просто
   блокировался (иначе клиент ушёл бы по v6 мимо списков и мимо туннеля,
   пока TPROXY была только про IPv4) — с переходом на sniffing-based
   routing зеркалить TPROXY на v6 стало дёшево (не нужно дублировать
   DNS-обвязку), сделано и проверено — см. «IPv6 — реализовано и
   проверено» ниже.

Обвязка: procd вместо systemd, UCI вместо `state.json`, без LuCI.
Под снос относительно десктопной версии: sudoers, pkexec, GTK, трей, `.deb`,
второе ядро для legacy-транспортов (`quic`/`http` не нужны — у сервера XHTTP).

## Что уже написано

- `10-vless-tunnel.nft` → `/etc/nftables.d/` — один сет (`vless4_bypass`,
  ручной «всегда напрямую») и цепочка `vless_prerouting`: приватные сети и
  bypass — `return`, весь остальной TCP/UDP — `tproxy ip to :12345`.
  Решение по домену/IP из списков внутри этого TPROXY уже не принимается
  здесь — им занимается `routing.rules` в `config.json` (см. ниже).
  `vless_forward6` глушит IPv6 как раньше.
- `vless-tunnel.init` → `/etc/init.d/vless-tunnel` — procd. На каждом
  старте зовёт `vless-tunnel _build-config` (пересобирает `config.json` из
  сохранённой в UCI ссылки + текущих `domains`/`subnets` — так правки в
  списках применяются без повторного `set-link`), ждёт порт
  (`wait_for_port`), затем `route_up` (policy routing). На `stop` —
  `route_down`. Никакой dnsmasq/sets-обвязки больше нет.
- `vless-tunnel.config` → `/etc/config/vless-tunnel` — UCI.
- `vless-tunnel` → `/usr/bin/vless-tunnel` — разбор `vless://`, сборка
  `config.json` (VLESS + freedom outbound, sniffing, routing.rules из
  `domains`/`subnets`). Команды: `setup`, `set-link`, `on`/`off`, `status`,
  `test`, `doctor`, `uninstall`, внутренняя `_build-config`, отладочные
  `parse`/`make`.
- `vless-tunnel-web` → `/www/cgi-bin/vless-tunnel` + `vless-tunnel-redirect.html`
  → `/www/t.html` — минимальная веб-страница (не LuCI): статус, смена
  ссылки, on/off. Без пароля, только LAN. Ключ шифрования нигде не
  отображается.
- `install.sh` — качает/проверяет файлы (локально или по sha256 с
  `$VLESS_TUNNEL_BASE_URL`), ставит `xray-core`, убирает следы старой
  (dnsmasq-based) установки при апгрейде, накатывает nftables точечно (без
  `fw4 reload`), **перезапускает уже включённую службу**, если это
  переустановка (см. «Опасный момент», найден и закрыт при миграции на
  реальном роутере).

## Эволюция архитектуры: почему решение 3 переписано

Исходный план (см. историю) был проще: решение «туннель или напрямую»
принимала **nftables до Xray** — сеты `vless4`/`vless4_dns`, которые
dnsmasq заполнял при резолве доменов из списка (`nftset=` директива).
Внутри Xray — один outbound, никакого routing. Это работало и было
проверено на реальном железе (полный end-to-end: LAN-клиент → nftables
TPROXY → Xray → сервер → интернет), но по пути обнаружился ряд всё более
серьёзных проблем:

- Мелкие, но реальные баги: `dokodemo-door` должен слушать `0.0.0.0`, не
  `127.0.0.1` (иначе TPROXY-доставка молча проваливается); `tproxy to`
  без указания семейства не проходит проверку nftables в таблице `inet`;
  `nft -f` без предварительного `nft delete chain` задваивает правила в
  chain при каждом повторном применении (сеты при этом идемпотентны, в
  отличие от chain); `/etc/init.d/dnsmasq reload` (SIGHUP) не пересобирает
  внутреннюю структуру сопоставления доменов для `nftset=` — нужен именно
  `restart`.
- Структурная (не багом) проблема: `off` чистил `vless4_dns` для защиты от
  чёрной дыры (TPROXY на мёртвый Xray), но это создавало окно, где DNS-кэш
  клиента (браузер/ОС) переживал переключение, а сет — нет: уже
  резолвленный до выключения домен переставал тоннелироваться после
  включения, пока клиент не переспросит DNS заново. Почти починили точечно
  (выяснилось, что `route_down()` и так защищает от чёрной дыры, чистить
  сеты было не обязательно) — но это лечило только один частный случай
  более общей проблемы.
- **Главная, неисправимая в этой архитектуре проблема**: решение
  принималось по DNS-**наблюдению**. Если DNS-запрос клиента не проходит
  через роутер — например, DNS-over-HTTPS в браузере (подтверждено живьём:
  Firefox с `about:networking#dns` показал `TRR: true` и DoH к Cloudflare
  для всех запросов) — IP никогда не попадает в сет, и трафик молча идёт
  мимо туннеля. Симптом неотличим на глаз от «домен неправильно добавлен
  в список» или «баг в vless-tunnel», хотя сам механизм тегирования при
  этом работал совершенно исправно.

Посмотрели, как эту же задачу решают форкоп (sing-box, живьём на этом же
роутере) и v2rayA (Xray-core, по исходникам `github.com/v2rayA/v2rayA`) —
оба **не наблюдают DNS**, а перехватывают TPROXY весь трафик и распознают
домен через **sniffing** прямо из TLS SNI/HTTP Host в момент соединения,
уже внутри проксирующего ядра. Это устойчиво к DoH по конструкции: неважно,
как клиент узнал IP, важно что написано в самом соединении.

Владелец явно решил перейти на этот же принцип (не слепо копируя ни
форкоп, ни v2rayA — оба тянут либо fake-ip DNS-сервер, либо geosite.dat,
от чего в этом проекте осознанно отказались с самого начала). Итог —
текущая архитектура выше: TPROXY на всё, sniffing+routing.rules внутри
Xray, свой `domains`-список как inline-правила, никакого geosite.dat и
никакого dnsmasq.

## Проверено на реальном железе

**DoH-иммунность — ключевая проверка.** На Docker-стенде: LAN-клиент
(network namespace) настроен резолвить DNS **напрямую через `1.1.1.1`, в
обход роутера полностью** (имитация DoH). Соединение с явным HTTP
`Host: www.youtube.com` (домен есть в списке) на реальный Google IP —
`accepted tcp:142.251.157.4:80 [tproxy-in -> proxy]`, `tunneling request
... via 130.17.21.198:443` — протуннелировано, хотя роутер ни разу не
видел DNS-запрос к этому домену. Соединение с `Host: not-in-our-list` (нет
в списке) на тот же класс адресов — `[tproxy-in -> direct]`, корректно
пошло мимо туннеля. Оба направления подтверждены логом Xray.

**Живое подтверждение на настоящем роутере** (после деплоя новой
архитектуры): в логе — `accepted tcp:160.79.104.10:443 [tproxy-in ->
proxy]` (IP `api.anthropic.com`, домен есть в списке) и одновременно
`accepted tcp:149.154.167.x:443 [tproxy-in -> direct]` (Telegram MTProto —
`telegram.org` тоже есть в списке, но MTProto не TLS/HTTP, sniffing не
находит домен, падает в `direct` — это и есть ограничение sniffing-подхода
из архитектурных решений выше, не баг).

**Telegram/MTProto — закрыто.** Разгадка, почему у форкопа Telegram
работал, а у нас нет: у форкопа для категорий вроде `telegram` в
`community_lists` подтягивается не только список доменов, а ещё и
**отдельный готовый список IP-подсетей** из того же источника —
`/usr/lib/forkop/components/updates.uc`:
`telegram: [GITHUB_RAW_URL + "/Subnets/IPv4/telegram.lst", ...]`. Матчинг
по этим подсетям идёт по IP, в обход sniffing/DNS полностью — независимо
от протокола. Взяли тот же файл
(`itdoginfo/allow-domains/Subnets/IPv4/telegram.lst`, 10 CIDR) и вписали в
`subnets` на роутере. Живое подтверждение по логу Xray, тот же самый
IP до и после перезапуска службы: `accepted tcp:149.154.167.41:443
[tproxy-in -> direct]` (до) → `accepted tcp:149.154.167.41:443
[tproxy-in -> proxy]` (после). Домены и IP-подсети для одной категории в
этом источнике — две параллельные независимые подборки; при импорте
category-списков стоит помнить проверять оба варианта, не только `.lst`
из `Categories`/`Services`/`Russia`, но и `Subnets/IPv4/*.lst`.

**Опасный момент при миграции, найден и закрыт.** При апгрейде реального
роутера со старой архитектуры на новую: `install.sh` заменил файлы и
накатил новую (blanket) nftables-цепочку, но служба продолжала работать со
**старым** `config.json` (один outbound, без `routing`/`direct`) — то есть
несколько секунд **весь** LAN-трафик (уже перехватываемый новой цепочкой)
уходил в единственный VLESS-outbound, а не только домены из списка. Причина
— `install.sh` не перезапускал уже включённую службу после замены файлов.
Исправлено: `install.sh` теперь сам делает `/etc/init.d/vless-tunnel
restart`, если `vless-tunnel.main.enabled=1` на момент установки. Проверено
на стенде (повторный запуск install.sh при включённой службе триггерит
перезапуск) и задеплоено на реальный роутер.

**Миграция со старой архитектуры проверена дважды** (Docker-стенд и
реальный роутер): `install.sh` убирает confdir-остаток dnsmasq, старые
сеты `vless4`/`vless4_dns` удаляются после того, как ссылающаяся на них
chain уже пересоздана (иначе `nft delete set` падает с «Resource busy»).
На реальном роутере сохранённая ссылка сервера и список из 1229 доменов
пережили миграцию без изменений (`install.sh` не трогает существующий
`/etc/config/vless-tunnel`).

### CLI-команды

- **`setup [ссылка]`** — создаёт `/etc/vless-tunnel/{domains,subnets}`
  (шаблоны, не трогает существующие) и секцию UCI, опционально сразу
  `set-link`.
- **`set-link <ссылка>`** — парсит, собирает `config.json` (с текущими
  `domains`/`subnets`), проверяет ядром (`xray run -test`) во временный
  файл, только при успехе перезаписывает боевой конфиг и UCI; если служба
  запущена — сама `restart`.
- **`on`/`off`** — `uci set enabled` + `start`/`stop` (procd).
- **`status`** — enabled, разбор ссылки, состояние службы, policy routing,
  счётчик TPROXY-цепочки, число доменов/подсетей в списках.
- **`test`** — связь с сервером в обход nftables/TPROXY: `dokodemo-door` с
  фиксированным адресом на локальный тестовый порт. Не через HTTP-proxy —
  `wget` на OpenWrt для доменных целей через `http_proxy` падает с
  `Operation not permitted`.
- **`doctor`** — xray-core, живая nft-цепочка, валидность ссылки, число
  доменов/подсетей, `config.json` проходит `xray -test`.
- **`uninstall`** — точечный `nft delete` (не `fw4 reload` — рядом может
  быть другой сервис со своими правилами мимо `/etc/nftables.d`, как
  форкоп на этом роутере). Пакет `xray-core` не трогает.
- **`domains`** — печатает текущий список доменов (без комментариев).
- **`add-domain <домен>`** — добавляет в конец файла, если такого ещё нет
  (сверка идёт по уже очищенному от комментариев списку); базовая
  валидация (не пусто, без пробелов/`#`, есть точка). Пересобирает
  `config.json` и перезапускает службу, если она уже работает.
- **`remove-domain <домен>`** — удаляет только строку с самим доменом
  (после отсечения `#`-комментария), все остальные строки файла —
  заголовки категорий, пустые строки, другие домены — остаются как есть.
  Тоже пересобирает конфиг/перезапускает на лету.
- **`_set-domains-file <путь>`** (внутренняя) — заменяет файл `domains`
  целиком содержимым указанного файла; для веб-страницы, где правится один
  общий `textarea`, а не одна запись.

Мелкая деталь ucode: **функции не хойстятся**, как в JS — вызывающая
функция должна быть объявлена ниже вызываемой по файлу, иначе
`Type error: left-hand side is not a function` в рантайме, не при разборе.

### Управление доменами из веб-страницы

По просьбе владельца. На `/t.html` — карточка «Домены в туннеле»: быстрая
форма (одно поле, кнопка «Добавить» → `add-domain`) плюс сворачиваемый
`<details>` с `textarea`, куда подставляется **сырой** файл `domains`
(с комментариями, как есть — путь берётся через `uci get
vless-tunnel.main.domains`, не хардкодится) и кнопкой «Сохранить список»
(→ `_set-domains-file` через временный файл в `/tmp`). Удаление домена —
просто стереть его строку в textarea и сохранить; отдельной кнопки
«удалить» на каждую запись нет осознанно: список сейчас 1229+ строк,
кнопка на каждую была бы избыточной разметкой ради небольшого удобства.

Проверено на Docker-стенде (add/remove/bulk-save по отдельности и через
реальные POST-запросы формы, включая дедуп при повторном add, ошибку при
remove несуществующего, сохранение комментариев-заголовков категорий при
точечном remove, корректное HTML-экранирование `<script>` в textarea — не
исполняется, просто текст) и на реальном роутере (add→grep→remove→grep,
на боевом списке 1229 доменов, ничего не потеряно).

понимая масштаб побочного эффекта.

1. **Скорость direct-пути — закрыто, с числом.** Тариф — 600 Мбит/с
   (замерено с выключенным `vless-tunnel`, чистый потолок канала).
   С включённым туннелем на обычном (нетуннелируемом) сайте — 560 Мбит/с.
   То есть blanket TPROXY→Xray→freedom для `direct`-трафика (весь LAN
   теперь проходит через userspace, даже то, что в итоге не в туннеле —
   архитектурная цена перехода на sniffing, см. выше) стоит **~6.7%
   throughput** на этом железе (2×A53). Не катастрофично, но заметно и
   измеримо — если тариф вырастет (например, станет гигабитным), процент
   скорее сохранится, а не абсолютные Мбит/с, но не проверено.

   **Пропускная способность самого VLESS-туннеля (XHTTP+REALITY) —
   измерена, и это настоящее узкое место.** Метод: временный `config.json`
   с `dokodemo-door` на фиксированный публичный IP (`cachefly.cachefly.net`,
   стандартный публичный файл для speedtest'ов) через настоящий сохранённый
   `proxy`-outbound (тот же приём, что у команды `test`, но с большим
   файлом вместо короткого запроса; `/etc/hosts`-подменой сохранили
   правильные SNI/Host на подключении). Скачали `100mb.test` (104 857 600
   байт) дважды подряд для проверки повторяемости: **13.60с и 13.78с** —
   **~61 Мбит/с**, стабильно оба раза. Это заметно **ниже** и тарифа (600),
   и даже blanket-прямого пути (560) — на одно соединение узкое место не
   перехват трафика, а сам туннель (вероятно, CPU-стоимость XTLS/REALITY
   шифрования и padding на 2×A53 — в debug-логе на это указывают частые
   `XtlsPadding`/`Xtls Unpadding` записи).

   **Проверена и агрегация при нескольких параллельных соединениях**: те
   же `100mb.test` ×4 одновременно (той же схемой, `wget -O /dev/null` —
   на диск класть некуда, `/tmp` на роутере это RAM, при первой попытке
   писать на диск с 4 потоков сразу поймали `No space left on device` на
   ~30% каждого файла, 234 МБ RAM не резиновые). Итог: 419 430 400 байт за
   19с ≈ **~176.6 Мбит/с суммарно** — почти в 3 раза больше, чем на одно
   соединение (~61 Мбит/с), но не в 4 раза: рост сублинейный, похоже на
   упор в общий CPU-бюджет (2 ядра), а не на пропускную способность канала
   как такового. Практический вывод: одно медленное соединение (крупная
   закачка в одной вкладке) действительно упрётся в ~61 Мбит/с, а обычная
   браузерная нагрузка с несколькими параллельными соединениями получит
   заметно больше — но не пропорционально числу соединений.

   **Торрент — проверено вживую, ведёт себя ожидаемо и не проблема.**
   BitTorrent — свой бинарный протокол (не TLS/HTTP/QUIC), sniffing не
   извлекает домен ни для пиров, ни для трекера/DHT — весь такой трафик
   падает в дефолтное `direct`-правило, как и предсказывала архитектура.
   Реальный тест: `aria2c` с официальным торрентом (Big Buck Bunny,
   archive.org, легальный) на этой же LAN-машине, 420 МБ, до 38
   одновременных peer-соединений разом. В логе Xray — каждое соединение
   (порты 6881/6998/20806 и т.п., классика BitTorrent) корректно
   `[tproxy-in -> direct]`; при этом настоящий туннель (эта же сессия,
   `160.79.104.10:443` — Anthropic) продолжал штатно идти `-> proxy` в то
   же самое время, без сбоев. На роутере: `nf_conntrack_count` вырос с
   базовых 282 до 468 (+186 от пиров) и осел до 505 после завершения
   (естественно спадёт дальше по таймауту), память +11 МБ, `load average`
   не сдвинулся заметно (0.20→0.31 на пике, обратно к 0.20 после). То есть
   десятки одновременных мелких TCP/UDP-соединений через TPROXY→Xray→direct
   роутер (234 МБ RAM, 2×A53) переваривает без напряжения — предположение
   про «проблему с количеством соединений, не с throughput» из
   предыдущей версии этого пункта не подтвердилось на реалистичной
   нагрузке (38 пиров). Не проверялось: что будет при на порядок большем
   числе пиров (сотни) — редкая, но возможная ситуация для очень
   популярных раздач.
## IPv6 — реализовано и проверено

Раньше IPv6 у клиентов просто резался (`reject with icmpv6
admin-prohibited`). С новой sniffing-based архитектурой зеркалить TPROXY
на v6 оказалось действительно проще, чем в старой (не нужно дублировать
dnsmasq/nftset-обвязку — только второй `dokodemo-door`-инбаунд и второй
набор policy routing правил, sniffing/routing.rules общие для v4 и v6).
Сделано:

- `10-vless-tunnel.nft`: `vless_prerouting6` — зеркало `vless_prerouting`
  (те же приватные/локальные исключения: `::1`, `fe80::/10`, `fc00::/7`,
  `ff00::/8`, плюс `vless6_bypass` для ручного обхода), TPROXY на тот же
  порт `12345`. `vless_forward6` (старый reject) удалён.
- `vless-tunnel` (`build_config`): второй inbound `tproxy-in6`, `listen:
  "::"` (не `"::1"` — по той же причине, что и `0.0.0.0` вместо
  `127.0.0.1` у v4: TPROXY-доставка по чужому destination-адресу требует
  wildcard-адреса). `routing.rules` (домены/IP) общие для обоих inbound'ов
  — sniffing не зависит от версии IP.
- `vless-tunnel.init`: `route_up`/`route_down` теперь заводят и снимают
  `ip -6 rule`/`ip -6 route local ::/0 dev lo table 100` тем же способом,
  что и для v4.

**Проверено на Docker-стенде** (у стенда нет реального v6-WAN, так что
тест — тот же приём, что для DoH-обхода: синтетический v6-адрес назначения
+ HTTP `Host`): `Host: example.com` (в списке) на `[2606:4700::...]:80` —
`accepted ... [... -> proxy]`, счётчик `vless_prerouting6` вырос; `Host:
not-in-list` на другой v6-адрес — `-> direct`. Оба направления работают
так же, как и для v4. (Мелкая деталь: тег inbound'а — `tproxy-in` vs
`tproxy-in6` — в этой строке лога Xray иногда показывает не тот, что
реально принял соединение; не влияет на функциональность, ориентир —
счётчик нужной nft-цепочки и итоговое `-> proxy`/`-> direct`.)

**Задеплоено на реальный роутер** (обычной аккуратной миграцией) — но
провайдер на этом роутере IPv6 не выдаёт (`ip -6 addr show pppoe-wan`
пусто, только link-local). Фича корректно реализована и активна
(`nf_tproxy_ipv6` в ядре, policy routing поднят), но пока «спит» — заработает
сама, как только провайдер включит IPv6. Проверили важный краевой случай
на этом самом роутере: клиентские попытки IPv6 всё равно перехватываются
(счётчик `vless_prerouting6` растёт — устройства в сети пробуют IPv6,
видимо Happy Eyeballs), но при отсутствии v6-WAN `direct`-исходящие из
Xray падают так же быстро, как раньше падал явный ICMP-reject: `ip -6
route get <адрес>` на роутере сразу возвращает `Network unreachable`
(нет маршрута в принципе, не файрвол) — то есть регресса в скорости
Happy-Eyeballs-fallback на IPv4 быть не должно, хотя явно не
хронометрировали разницу в миллисекундах.

## Два независимых установщика — `install.sh` и `install-dns.sh`

По желанию владельца проект держит оба варианта архитектуры одновременно,
а не только текущий (sniffing-based). Не как временную ветку миграции —
это осознанный выбор: один раз можно вернуться к DNS-based варианту или
сравнить оба, если текущий вдруг не подойдёт в каком-то сценарии.

- **`install.sh`** — основной, sniffing-based (см. «Архитектурные решения»
  выше). Файлы без суффикса: `vless-tunnel`, `vless-tunnel.init`,
  `vless-tunnel.config`, `10-vless-tunnel.nft`.
- **`install-dns.sh`** — альтернативный, исходный DNS-based вариант
  (nftables решает до Xray, по членству IP в сете, который заполняет
  dnsmasq через `nftset=` при резолве). Файлы с суффиксом `-dns`:
  `vless-tunnel-dns`, `vless-tunnel-dns.init`, `vless-tunnel-dns.config`,
  `10-vless-tunnel-dns.nft`.

Оба ставятся в **одни и те же** системные пути (`/usr/bin/vless-tunnel`,
`/etc/init.d/vless-tunnel`, `/etc/nftables.d/10-vless-tunnel.nft`,
`/etc/config/vless-tunnel`) и используют **одни и те же** имена
nftables-цепочек (`vless_prerouting`/`vless_prerouting6`) — поэтому на
роутере одновременно активен только один вариант, а установка другого
аккуратно вытесняет предыдущий (оба install-скрипта сносят chain
предыдущего варианта перед созданием своего и чистят чужие сеты —
`install.sh` снимает `vless4`/`vless4_dns`/`vless6`/`vless6_dns`,
оставшиеся от `-dns`-варианта; `install-dns.sh` не оставляет за собой
ничего лишнего у sniffing-варианта, кроме уже убираемого `10-vless-tunnel.nft`/
chain). CLI-команды (`setup`, `set-link`, `on`/`off`, `status`, `test`,
`doctor`, `uninstall`, `domains`/`add-domain`/`remove-domain`) и формат
вывода `status` одинаковы у обоих вариантов — веб-страница
(`vless-tunnel-web`) одна на двоих и не знает, какой из них установлен.

**Найденный и исправленный баг `-dns`-варианта: `nftset=` для AAAA
молча терялся, если IPv4- и IPv6-часть были отдельными директивами.**
Изначально `dns_up()` писал на каждый домен по две строки:

```
nftset=/example.com/4#inet#fw4#vless4_dns
nftset=/example.com/6#inet#fw4#vless6_dns
```

На стенде это давало странную картину: A-записи корректно тегировались
в `vless4_dns` (`nftset add 4 ...` в логе dnsmasq), а AAAA-записи
резолвились нормально (было видно в `nslookup` и в `reply ... is
2a06:...` в логе), но `vless6_dns` оставался пустым — вообще без строки
`nftset add 6 ...` в логе, то есть dnsmasq даже не пытался её добавить.
Причина — не в кастомных сетах и не в правах/джейле (проверено запуском
`dnsmasq` вручную вне `ujail`, с `--log-queries`): две отдельные
`nftset=`-директивы на один и тот же домен не складываются друг с
другом — dnsmasq запоминает только первую (по IPv4), а вторая молча
теряется. Фикс — обе семьи одной директивой, через запятую:

```
nftset=/example.com/4#inet#fw4#vless4_dns,6#inet#fw4#vless6_dns
```

После этого обе записи (`vless4_dns` и `vless6_dns`) корректно
наполняются на одном резолве. Проверено на стенде: `nslookup example.com`
через живой сервис одновременно наполнил оба сета правильными адресами;
дополнительно проверена v6-классификация ручного `subnets` (строки с
`:` уходят в `vless6`, без — в `vless4`) и полный цикл `off`/`on`.

**Обе миграции (sniffing↔`-dns`) проверены вживую на стенде** —
`install.sh` поверх уже установленного `-dns`-варианта и `install-dns.sh`
поверх уже установленного sniffing-варианта: chain/сеты пересобираются
чисто в обе стороны, служба остаётся рабочей, DNS-тегирование продолжает
работать после переключения.

**`install-dns.sh` задеплоен и проверен на реальном роутере** (владелец
уже держал на нём `dnsmasq` с поддержкой `nftset` и настроенный `confdir`
с прошлого раза — апгрейд пакета и его реконфигурация не потребовались,
только файлы сервиса и nftables-правила). `doctor`/`status` зелёные,
ссылка/домены/подсети (1229/10) сохранились с прежней установки без
изменений, `youtube.com`/`anthropic.com` корректно тегируются в
`vless4_dns`/`vless6_dns` при резолве **с самого роутера**.

Отдельно всплыл и разобрался ложный тревожный сигнал: при проверке с
LAN-клиента (ноутбук владельца) резолв `anthropic.com` иногда не давал
тега в `vless4_dns`, что сперва выглядело как повторение той же болезни
DoH-обхода, ради которой изначально ушли от этой архитектуры. Причина
оказалась не в роутере: на клиентском устройстве параллельно работает
отдельное VPN-приложение («локальный туннель» в терминологии владельца,
не связанное с этим проектом и не с `forkop`), которое перехватывает
DNS/трафик на уровне устройства, пока включено, — тесты через него шли
мимо роутера целиком и не показывали его реальное поведение. С выключенным
сторонним VPN-приложением резолв с того же устройства напрямую через
роутер (`dig @192.168.1.1`) корректно тегирует IP в обе стороны (v4/v6),
трафик идёт через `vless4_dns`, соединение с интернетом стабильно. Вывод:
собственный `-dns`-вариант работает штатно; спутать его с DoH-обходом
при диагностике легко, если на клиенте есть посторонний VPN — стоит
явно проверять, что он выключен, прежде чем делать выводы о поведении
роутера.

## DNS роутера в сторону апстрима — через DoH (`https-dns-proxy`)

Отдельный вопрос от предыдущего раздела: там — резолвит ли *клиент* через
роутер, здесь — куда сам *роутер* шлёт свой DNS-запрос дальше. До этого
шёл plaintext-запрос (UDP:53) к DNS-серверам провайдера
(`/tmp/resolv.conf.d/resolv.conf.auto`, пришли по PPPoE) — виден
провайдеру/DPI как есть, хотя итоговое соединение уже в туннеле.

Поставлен `https-dns-proxy` (официальный пакет из фида OpenWrt,
поддерживает stangri/mossdef-org, форк известного
`aarond10/https_dns_proxy` — не GitHub-релиз, собран и подписан
билд-ботами OpenWrt, тот же уровень доверия, что у всех остальных
пакетов). dnsmasq теперь форвардит на `127.0.0.1:5053`, а тот шифрует и
шлёт на `https://cloudflare-dns.com/dns-query` (1.1.1.1 выбран за более
внятную политику логов и то, что блокировать Cloudflare целиком дороже
для провайдера/цензора, чем узкоспециализированный резолвер). Из
дефолтных двух инстансов (Cloudflare + Google) оставлен только
Cloudflare — второй убран из UCI, чтобы не гонять два процесса зря.
`force_dns` (пакет умеет силой заворачивать/резать DNS-трафик LAN-
клиентов на порт 53/853 в свою сторону) оставлен выключенным — это
отдельная функция сверх задачи «сменить апстрим самого роутера», может
конфликтовать с тем, как `-dns`-вариант сам решает, что тегировать, и
не была тем, о чём просили.

Проверено на стенде и на реальном роутере: резолв идёт через DoH,
`vless-tunnel`-тегирование (`vless4_dns`/`vless6_dns`, обе семьи) поверх
этого продолжает работать без изменений — DoH меняет только то, как
dnsmasq достаёт ответ, а `nftset=`-триггер срабатывает на forward-ответе
так же, как и раньше.

**Грабли при установке:**

- После `apk add`/UCI-редактирования конфига (удаление второго,
  google-инстанса) в `/etc/config/dhcp` остаётся мусорная запись
  `server=127.0.0.1#5054` (и в `doh_server`/`doh_backup_server`) —
  `https-dns-proxy` не подчищает её сам при простом `restart`.
  Убирается вручную (`uci del_list dhcp.@dnsmasq[0].server=...` и т.п.)
  + `/etc/init.d/dnsmasq restart`.
- Параллельный запуск `apk add https-dns-proxy` (у которого свой
  post-install сам делает `enable`+`start`) и ручного вызова
  `/etc/init.d/https-dns-proxy start` в это же время — гонка за
  `/tmp/lock/procd_https-dns-proxy.lock`, оба зависают намертво. Просто
  не трогать сервис руками, пока не закончится `apk add`.
- **Реальный роутер, а не стенд**: `apk add https-dns-proxy` отказал —
  `breaks: forkop-1.0.5[!https-dns-proxy]`. Пакет `forkop` в своих
  метаданных явно объявляет несовместимость (форкоп сам заведует DNS
  похожим образом через sing-box). По решению владельца `forkop` вместе
  с `luci-app-forkop`/`luci-i18n-forkop-ru` удалён с роутера полностью —
  осознанный отказ от него как от резерва ради DoH, необратимо без
  переустановки.
- **Важная находка при удалении forkop**: вместе с ним снёсся
  `kmod-nft-tproxy`/`kmod-nf-tproxy` — оказалось, что эти модули ядра
  стояли на роутере только как зависимость `forkop`, а не нашего
  `vless-tunnel`, хотя нужны именно нашему TPROXY. Модуль, уже
  загруженный в память, работал и после удаления пакета — но пропал бы
  с диска и не поднялся бы при следующей перезагрузке. Исправлено сразу
  (переустановлены явно) и заодно закрыто на будущее: `install.sh` и
  `install-dns.sh` теперь сами явно ставят `kmod-nft-tproxy`/
  `kmod-nf-tproxy`, не полагаясь на то, что их притянет что-то стороннее.
- **Автоматическая установка DoH (этап 6 обоих установщиков) ломала
  `set -e` весь install на самом обычном, не крайнем случае.**
  `apk add https-dns-proxy` ставит по умолчанию ДВА инстанса
  (Cloudflare + Google); наш скрипт оставляет только Cloudflare и чистит
  оставшийся от второго инстанса мусор в `/etc/config/dhcp`
  (`127.0.0.1#5054`). На чистой установке этого мусора ещё нет —
  `uci del_list`/`uci delete` на несуществующем значении возвращают
  ненулевой код даже с `-q`, и `set -e` валил весь install прямо после
  строки «https-dns-proxy установлен — настраиваю», хотя по факту всё
  уже настроилось. Исправлено (`|| true` на этих командах). Проверено
  вживую на реальном роутере: до фикса — падало на 100% свежих
  установок, после — доходит до `enable`/`restart`.
- **Отдельно от этого: `apk add https-dns-proxy` сам стартует службу
  через свой post-install, и наш собственный `restart` сразу следом
  иногда ловит гонку за procd-локом** — не зависает намертво (как в
  сценарии с двумя параллельными ручными вызовами на стенде раньше), а
  возвращает ошибку. Сделано нефатальным (`|| log "предупреждение..."`),
  но реальная причина этой ошибки на живом роутере оказалась глубже:
  рестарт `https-dns-proxy`/`dnsmasq` пересобирает свою nftables-таблицу
  `https_dns_proxy_notrack` (conntrack-исключения для собственного DNS-
  трафика прокси), и это на мгновение рвёт conntrack-состояние для *уже
  установленных* TCP-соединений — включая ту самую SSH-сессию, из-под
  которой запущен install. Дважды воспроизведено вживую: SSH-соединение
  обрывается ровно на этом шаге, но сам install на роутере всё равно
  доходит до конца успешно (проверено переподключением сразу после —
  `doctor` зелёный, `https-dns-proxy` с одним Cloudflare-инстансом,
  `force_dns` выключен). Не баг логики скрипта — если ставите
  `install*.sh` по SSH и на этапе 6 сессия оборвалась, это ожидаемо;
  переподключитесь и проверьте `vless-tunnel doctor` — почти наверняка
  всё уже настроилось.

## Установка «запустил и всё настроилось»

По просьбе владельца оба установщика теперь сами делают две вещи, которые
раньше требовали ручной работы после `sh install*.sh`:

- **Снэпшот `domains`/`subnets` кладётся в репозиторий** (файлы `domains`,
  `subnets` рядом с install-скриптами, попадают в `FILES=`/`sha256sums`
  как любой другой файл проекта) и копируется в
  `/etc/vless-tunnel/{domains,subnets}` при установке — **только если
  файла там ещё нет**, той же логикой, что и `/etc/config/vless-tunnel`:
  свой список поверх снэпшота install-скрипт не перезатирает. На первой
  установке — сразу 1229 доменов / 10 подсетей, без ручного импорта.
- **DoH (`https-dns-proxy`) ставится автоматически, но мягко.** Отдельный
  этап 6 в конце обоих установщиков: `apk add https-dns-proxy`, и если он
  прошёл — настройка (один инстанс на Cloudflare, `force_dns` выключен,
  чистка стейл-записи `#5054`, `restart`) — та же последовательность, что
  проверяли вручную на стенде и роутере. Если `apk add` не прошёл
  (типичная причина — конфликт с `forkop`, `breaks: forkop-1.0.5[!https-
  dns-proxy]`), установка **не падает**: печатается предупреждение,
  остальной install доводится до конца, DNS роутера остаётся как был.
  Осознанно НЕ сносим `forkop` автоматически ради этого — удаление
  форкопа (и вместе с ним `kmod-nft-tproxy`/`kmod-nf-tproxy`, см. выше)
  было отдельным осознанным разовым решением владельца, не то, что должно
  происходить само по себе при каждой установке.

Проверено на стенде: `vless-tunnel uninstall` → `sh install-dns.sh` с
нуля — `doctor` показывает «доменов в списке: 1229, IP-подсетей: 10» и
`https-dns-proxy` (был поставлен ранее в этой же сессии) корректно
распознаётся уже установленным, шаг пропускается без ошибок.

## Чего не делать

- Не тащить LuCI-приложение. Владелец явно отказался от комбайна.
- Не добавлять community-списки и подписки как живой, обновляющийся
  источник — списки свои, руками. (Разовые статические снимки чужих
  списков, явно запрошенные владельцем и помеченные источником/датой,
  делали — файлы `domains`/`subnets` в репозитории; это не подписка,
  апстрим не отслеживается, обновляется только руками при желании.)
- Не ставить geo-файлы (`geosite.dat`/`geoip.dat`) — свой inline-список
  в `routing.rules` вместо них, осталось верным и после смены архитектуры.
